Fine-tuning vs Prompting: When to Train and When Not To

🎯 What you'll be able to do: Decide systematically between prompting, RAG, tools, and fine-tuning — and understand LoRA basics.
Roni · Play the lecturer

The decision tree

The order to try: (1) prompt + few-shot — it solves more than you'd think; (2) RAG — when factual, updating knowledge is missing; (3) tools — when you need an action or live data; (4) fine-tuning — last, and only if what's missing is style, rigid format, or latency. Fine-tuning does not reliably teach new facts — it teaches behavior. A legitimate sign: if your prompt is already 4,000 tokens of instructions and examples, folding it into the weights is exactly the case fine-tuning was invented for.

When fine-tuning truly wins

Three cases: (1) consistent style — the model must write like your brand, classify into a weird schema, sound like Roni; (2) rigid format at scale — a million calls that pay for themselves: a small fine-tuned model can beat a frontier model on a narrow task at a fraction of the price and half the latency; (3) prompt compression — fewer tokens per call, lower cost forever. And what it's not: updating knowledge (that's RAG), arithmetic (that's tools), general reasoning improvements (that's a bigger model). Key test before training: do 50 perfect examples in the prompt get you close to the target? If yes — you haven't earned fine-tuning yet.

LoRA: training without burning GPUs

Full training of a billion-parameter model is expensive and usually unnecessary. LoRA freezes the model and adds a pair of small low-rank matrices (r=8–64) to every attention layer — you train only those, under one percent of parameters. QLoRA adds 4-bit quantization of the base — suddenly you can fine-tune an 8B model on a consumer GPU.

`python

from peft import LoraConfig

config = LoraConfig(r=16, lora_alpha=32,

target_modules=['q_proj', 'v_proj'],

lora_dropout=0.05, task_type='CAUSAL_LM')

`

Bigger r = more capacity, more overfitting. Start at r=16. The output is a small adapter (tens of MB) loaded onto the base.

Data: where training is actually decided

1,000 excellent examples beat 50,000 mediocre ones — every single time. Format: chat messages in exactly the schema you'll run in production (system/user/assistant), because the model is trained on the format it will meet.

`json

{"messages": [{"role": "system", "content": "You are a bank agent."}, {"role": "user", "content": "What is a credit line?"}, {"role": "assistant", "content": "A credit line is..."}]}

`

Before a big run: a train/val split and a small eval (100 cases) after every epoch. If the train-val gap widens — the data leaks or the model memorized, it didn't learn.

Copy-ready prompt

The 'do we even need fine-tuning yet' test — run before considering training: ``` Perform the following task exactly per the 5 provided examples. If unsure about the format, follow example 3. Task: {input} ```

One training data line (JSONL, chat format): ```json {"messages": [{"role": "user", "content": "Summarize the complaint"}, {"role": "assistant", "content": "{\"severity\": \"high\", \"topic\": \"billing\"}"}]} ```
