RAG Quality: Evaluation and Iteration

🎯 What you'll be able to do: Build an evaluation set for RAG, measure recall and answer quality, and know what to improve first.
Roni · Play the lecturer

The golden set: 30 questions worth more than a model

Before any optimization: collect 30–50 real questions from users (logs, support, colleagues) and mark for each which chunks contain the correct answer (gold chunks). Important: include both questions the system already answers well and ones it currently fails — otherwise you only measure what already works. A distribution across question types (factual, comparative, 'not answerable from the docs') is mandatory — the third type is what breaks most systems and nobody tests it.

Retrieval metrics: before the model

Retrieval is measured before generation because it's cheap to measure and causes most failures: recall@k — is the right chunk inside the top-k; MRR — how highly it ranked; hit_rate — percentage of questions with at least one hit.

`python

def recall_at_k(results, gold, k=5):

topk = {r['id'] for r in results[:k]}

return len(topk & set(gold)) / len(gold)

`

Practical target: recall@5 above 0.85 before touching the answer prompt. If it's 0.6 — fix chunking and search, not the model.

Answer metrics: an LLM judge with a rubric

The answer is measured on three axes: faithful (grounded in the passages — no hallucinations), relevant (answers the question), complete (doesn't miss half). A strong judge LLM scores each axis 1–5 against a written rubric, with the passages and the answer under review in front of it. Calibration is mandatory: manually grade 10 answers yourself, compare with the judge, and only trust it if agreement is high. Always keep the judge's raw output for inspection — a metric you can't debug isn't a metric, it's decoration.

The iteration loop: what to improve first

A winning order, cheapest first: (1) ingest bugs — missing files, broken parsing, duplicates; (2) chunking and overlap; (3) hybrid + rerank; (4) query templates; (5) number of passages in the prompt; (6) the model. Every change runs against the same golden set, and the result goes into one table — date, change, recall@5, judge score. Without such a table you're just rearranging furniture and hoping. With it, every 'let's improve' conversation becomes a conversation about numbers — and that's a win in any meeting.

Copy-ready prompt

Faithfulness judge (LLM-as-judge): ``` Passages: {context} Answer: {answer} Is every claim in the answer directly supported by the passages? Return JSON: {"supported": true/false, "unsupported_claims": ["..."], "verdict": "faithful|hallucinated|partial"} ```

Quick measurement before any upgrade: ```python score = sum(recall_at_k(search(q), gold[i]) for i, q in enumerate(questions)) / len(questions) print(f'recall@5 = {score:.2f}') ```
