Cost & Latency Engineering: Caching, Batching, and Model Routing

🎯 What you'll be able to do: Systematically reduce the cost and latency of an LLM system without hurting quality.
Roni · Play the lecturer

Measure first: p50, p95, and cost per request

Optimization without measurement is faith, not engineering. Three numbers every system must report: p50 and p95 of time-to-first-token (TTFT) and to last token, average cost per request, and a breakdown by request type.

`python

import time, statistics

lat = []

for req in sample:

t = time.time(); resp = call(req); lat.append(time.time() - t)

print(statistics.median(lat), sorted(lat)[int(len(lat)*0.95)])

`

p95 is what users feel — they don't live in the average, they live in the tail. And cost by request type will reveal that ten percent of paths burn sixty percent of the budget. That's where you start.

Cache layers

Four layers, cheapest to smartest: (1) prompt caching — fixed prefix at the top (system + tools), up to 90% off input; (2) exact-result cache — identical repeat requests keyed by message hash + prompt version; (3) semantic cache — similar enough (cosine over a threshold like 0.95) returns a stored answer — careful, good for factual questions, risky for sensitive conversations; (4) tool-result cache — an expensive API call the agent repeats over and over, keyed by TTL. Before every layer: measure the hit rate. A cache with 5% hits is maintenance pain, not savings.

Batching: what isn't needed now is cheaper later

Most providers give 50% off the Batch API — an asynchronous run of thousands of requests with no real-time requirement, results within hours. Perfect for: bulk email classification, archive data extraction, generating embeddings, building datasets. The rule: anything the user isn't waiting on right now is almost always cheaper in batch. What is interactive — that's where you play with latency: streaming (a fast first token feels twice as fast as it is), prefetching predictable tools, and running independent calls concurrently.

Routing: the cheap model goes first

Not every request needs the big model. A cascade: try the cheap model, escalate only on a sign of trouble — invalid output, or a classifier flagging complexity.

`python

def route(msg):

if simple_intent(msg):

return call('gpt-4o-mini', msg, fallback=True)

return call('gpt-4o', msg)

def call(model, msg, fallback=False):

out = run(model, msg)

if fallback and not valid(out):

return run('gpt-4o', msg)

return out

`

In practice, 60–80% of traffic resolves on the cheap model. Keep measuring: how many requests escalated, and accuracy on the golden set — a router that's wrong on 5% of cases eats its savings in bugs.
