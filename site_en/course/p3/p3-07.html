Multi-Agent Orchestration: Router, Critic, and Planner-Executor

🎯 What you'll be able to do: Choose and implement the right multi-agent pattern — and know when a single agent is enough.
Roni · Play the lecturer

First: do you even need multiple agents

Multi-agent is justified when there are: genuinely different specializations (different tools, conflicting prompts), a need for context isolation (one agent with 50 tools is a mess — two with 10 focused ones win), or true parallelism. What's not justified: 'splitting into agents' because it sounds advanced. My rule: start with one agent and a good tool loop, and split only for a measurable reason — accuracy drop, high cost, or a giant prompt trying to be everything. Splitting is a refactor, not a feature.

Router: dispatch to the right specialist

The simplest and most profitable pattern: a light agent (small model, temperature=0) that classifies the request and routes it to a specialist. Double win: short, focused prompts per specialist, and cost-aware routing — simple requests to a cheap model.

`python

ROUTE = 'Classify the request into one of: billing | technical | sales | other. Return one word.'

route = llm(ROUTE + '\n' + user_msg, temperature=0)

answer = EXPERTS[route.strip()](user_msg)

`

Mandatory: a fallback for other, and a log of every dispatch — a quiet router is one you'll never know is wrong.

Critic: draft, then critique

Generate a fast answer, then a second agent — with a deliberately different prompt — critiques it: does it answer the question? Does the code run? Any hallucinations? If the critique finds a problem, return to the creator with the notes (up to 2 rounds).

`python

draft = creator(task)

for _ in range(2):

review = critic(task, draft)

if review['ok']:

break

draft = creator(task + '\nFix: ' + review['issues'])

`

The trick: give the critic a hostile, detailed prompt ('hunt for errors, don't be nice'), and a clear stopping condition. Without one, agents will argue forever — on your tab.

Planner-Executor: big tasks

For multi-step tasks ('compare three travel packages and write a summary'): the planner produces a list of steps phrased as testable actions, the executor runs each with its tools, and a replanner updates when a step fails. Three laws: (1) every step is an action with defined input and output, not 'think about'; (2) one shared state that everyone reads and writes; (3) maximum depth — a plan that loops on itself gets cut. And in parallel: independent steps run async, dependent steps in order — the plan is a graph, not a list.

Copy-ready prompt

Production router prompt: ``` You are a router. Classify the user request into exactly one category: billing, technical, sales, smalltalk, other. Answer with a single word only, no reasoning. Request: {message} ```

Hostile critic prompt: ``` Task: {task} Draft: {draft} Check ruthlessly: (1) Is every part of the task addressed? (2) Is any claim unsupported by the data? (3) Will the code run? Return JSON: {"ok": bool, "issues": ["..."], "missing": ["..."]} Don't be polite. Find problems. ```

Build a support bot with three agents: a router, two specialists (orders and technical), and a critic that verifies the answer includes an order number when one exists. Run 15 sample tickets, log the router's decisions, and measure how many tickets went to the wrong specialist.
