Project 3: Multi-Agent Content Pipeline

🎯 What you'll be able to do: Build a multi-agent content pipeline — researcher, writer, and editor agents coordinating through a LangGraph graph — and deploy it as a working product with evals.
Alex · Play the lecturer

Why multiple agents

One agent with 20 tools and one giant prompt confuses itself — the failure you met in Lesson 11. The multi-agent answer: decompose. Each agent gets a small toolset, a focused prompt, and one job:

  • Researcher: search + retrieve, output = a sourced brief (claims with links).
  • Writer: draft from the brief ONLY — no new facts allowed, by prompt contract.
  • Editor: LLM-as-judge rubric (accuracy-to-brief, tone, structure, length) with a 1–5 score per criterion; below threshold, send back with the critique attached.

In LangGraph: three node-pairs (model + tools each), a shared PipelineState carrying the brief, draft, scores, and revision count, and a conditional loop editor → writer capped at 2 revisions. The cap is not optional — it's what makes the graph terminate.

The contracts between agents

Multi-agent systems live and die on their interfaces. Define them as Pydantic models before writing any prompts:

`python

class Source(BaseModel):

claim: str

url: str

class Brief(BaseModel):

topic: str

sources: list[Source]

class Draft(BaseModel):

content_markdown: str

citations: list[str]

class Critique(BaseModel):

scores: dict[str, int] # accuracy, tone, structure

verdict: Literal["approve", "revise"]

notes: str

`

Because agents pass validated objects — not free text — a bad writer output fails at the schema, not in the reader's hands. This is Lesson 7 scaled up to system design, and it's the single best answer to the interview question 'what's hard about multi-agent systems?' Contracts.

Observability is the feature

When a three-agent pipeline produces a mediocre result, 'which agent failed?' must be answerable in one minute. Log every hop: the brief (with sources), each draft, each critique with scores, token counts per agent, and total wall time. Surface it in the UI — a collapsible 'pipeline trace' panel. This transforms the product from a magic box into an inspectable system, and it's precisely how real agent platforms (LangGraph-based ones included) sell themselves. Your eval suite: end-to-end — run 5 topics, editor-score the outputs, assert revision counts stay under the cap, and track total cost per run. Cost per run in the README is a beautiful, senior-sounding number.

Ship and position it

Deploy like the others (FastAPI + Docker + free tier, public URL), with a queue — pipeline runs take a minute, so submit a topic, get a job ID, poll for the result. Demo mode: two pre-run example topics so the link never shows an empty screen. Position it in the README as what it is: 'a LangGraph multi-agent pipeline with typed agent contracts, an evaluator loop, and full traces.' That sentence hits multi-agent (16%), LangGraph (13%), evals (9%), and observability in one line. Then write the blog-post version — a short 'how I built it' (Lesson 20 turns it into LinkedIn gold). Next lesson: your capstone — a personal-assistant agent that ties the whole course together.
