Function Calling and Tools — the Concepts

🎯 What you'll be able to do: Understand how models call functions and APIs — schemas, the tool loop, error handling — without needing to be a programmer.
Alex · Play the lecturer

The menu and the order

Function calling works like a restaurant. You (the builder) give the model a menu: a list of tools, each with a name, a plain-language description, and a schema — the exact fields and types it accepts. The model never executes anything. It reads the task, picks a tool, and returns a structured order: {"tool": "send_email", "to": "dana@corp.com", "subject": "Order confirmed"}. Your code or platform executes it and returns the result. The model reads the result and continues. Menu in, order out, dish back — that's the whole protocol.

Writing tool descriptions is prompting

The model chooses tools by reading your descriptions — so a vague description means wrong choices. Bad: "a function for dates." Good: "Check availability for a meeting. Use when the user wants to schedule. Requires an email address and a date. Do not use for cancellations." Same few-shot and clarity rules from Module 2 apply verbatim. Practical habits: keep the toolset small (5-8 tools; beyond that, models grab the wrong one), give tools non-overlapping jobs, prefer enums for parameters, and require an ID everywhere it matters. Most 'dumb agent' bugs are actually a bad menu.

When the call fails

Real tools fail: the email address doesn't exist, the API times out, the date is invalid. Amateurs let the agent crash or hallucinate success. Professionals design the loop for failure:

  • Return the error to the model — {"error": "address not found"} — so it can retry or ask the user. It's surprisingly good at this.
  • Set limits — max 3-5 tool calls per task before stopping and summarizing for a human.
  • Log every call — the timestamped story of what the agent did. Your audit trail and your debugging lifeline, both.
  • Validate before executing — confirm destructive actions (delete, send, pay) with a human or a rule.

Error handling, not intelligence, is what separates production agents from demos.

Where you'll meet this

You'll touch function calling in four places: (1) no-code platforms — you'll describe tools in their UI, same concepts, no code; (2) MCP — the Model Context Protocol — the emerging 2026 standard that lets any agent plug into shared tool servers, dragging ChatGPT, Claude, and IDEs into one ecosystem; (3) APIs — calling a model programmatically, where you'll pass tool schemas as JSON; (4) interviews — 'explain how function calling works' is a top-5 screening question for AI roles, and now you can answer it in menu-and-order terms. Reading this machinery fluently is your edge as a non-programmer.

Copy-ready prompt

I want to give my agent these capabilities: [LIST — e.g. send email, check calendar, search docs]. For each, write a tool definition: name, one-line description, parameters with types, and when NOT to use it.

My agent keeps calling the wrong tool or invents parameters. Here are my tool definitions: [PASTE THEM]. Diagnose the likely causes and rewrite the weakest definition.

💪 Exercise

Design (on paper or in a no-code platform) a toolset for your Lesson 10 agent: 3-5 tools with full schemas. Then simulate a failure: write what your agent should return to the model when one tool fails, and what it should do on the third consecutive failure.
