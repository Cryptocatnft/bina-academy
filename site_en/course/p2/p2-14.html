Portfolio Project 2: Document Analyzer (RAG Basics)

🎯 What you'll be able to do: Build a question-answering agent over a pile of documents using retrieval — the RAG pattern behind most real-world AI systems.
Alex · Play the lecturer

Why RAG exists

Two hard limits force RAG on us: context limits — documents don't fit in the window (Lesson 3) — and grounding — models hallucinate when answering from memory (Lesson 4). RAG solves both: at build time you split documents into chunks, convert each to an embedding (a numeric fingerprint of meaning), and store them in a vector database. At question time you embed the *question*, find the most similar chunks, and hand only those to the model to answer from. Simple mental model: RAG is a search engine feeding a summarizer — a librarian who fetches the right pages, and a writer who reads only those pages.

Step 1: Your corpus and chunking (30 min)

Pick 10-20 documents of one type — contracts, policies, research PDFs, or generate them with AI (fine for a portfolio, just say so). Chunking is the craft: split each document into pieces of ~300-500 words, with 10-20% overlap so ideas that straddle a boundary survive. Keep metadata on every chunk — source filename, section, page — because it becomes your citation. If you use a no-code RAG tool (ChatGPT Projects, Claude Projects, Notion AI, or a vector-store template in n8n/Flowise), chunking happens for you — but you must be able to *explain* it, because interviewers always ask: 'why does chunk size matter?' Now you know.

Step 2: Retrieval and the answer (45 min)

The user asks a question. Your system embeds it, pulls the top 4-8 most similar chunks, and builds a prompt: "Answer only from the passages below. Cite the source for each claim. If the answer isn't there, say so." The non-negotiable feature: citations — every claim tagged with the document and section it came from, because that's what makes output *verifiable* (Lesson 4 habits, systematized). Test the sad path deliberately: ask questions that are NOT in the documents and confirm the agent says 'not found' instead of improvising. A RAG system that admits ignorance is a professional one; one that always answers is a liability.

Step 3: Evaluate, document, ship (45 min)

Build a 15-question eval set: 10 answerable from the documents (with the correct source noted), 3 that are not, 2 cross-document questions requiring synthesis from multiple files. Score each answer: correct + correctly cited / correct but wrong citation / wrong / hallucinated. Tweak chunk size or retrieval count and re-run — this loop is *the* RAG skill. Write the README with your architecture, a 'how it works' explanation in plain words, the eval table, and design decisions. Deploy wherever your platform allows. This is portfolio artifact #2, and it's the one most likely to get you hired — RAG is what companies actually deploy. Say the words 'retrieval-augmented generation' in your README and in your sleep.

Copy-ready prompt

You are a RAG system. I will give you passages and a question. Answer ONLY from the passages. Cite each claim like [doc1, section 2]. If the answer is not in the passages, say exactly: 'Not found in the provided documents.' Question: [YOUR QUESTION]. Passages: [PASTE CHUNKS]

I'm building a RAG demo over [DOCUMENT TYPE]. Generate a 15-question evaluation set: 10 answerable, 3 deliberately unanswerable, 2 requiring synthesis across documents. For the answerable ones, note the expected answer and source.

💪 Exercise

Build and ship the analyzer: 10+ documents chunked with metadata, retrieval with citations, 15-question eval set scored and logged, README with architecture and design decisions. Verify the unanswerable questions return 'not found' — that's the behavior that proves you understand grounding.
