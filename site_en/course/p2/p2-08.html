The daily workflow

Git is a time machine for code; GitHub is where the timeline lives publicly. The professional loop:

`bash

git init && git add . && git commit -m "first ticket classifier"

git branch feature/streaming

git switch feature/streaming

# ...work, then: git add -p && git commit -m "add streaming"

git push -u origin feature/streaming # then open a PR

`

Commit small and often, with messages that say *why* ('retry on 429 to survive rate limits') not what. Branch per feature. Open a pull request even on your own repos — it documents your thinking and proves you know the team workflow employers assume. If your history is one giant 'final version' commit, you look like an amateur. If it's clean, you look hireable.

Protect your secrets

The fastest way to burn money as a beginner: commit an API key. Bots scrape GitHub for leaked keys within minutes of a push. Defenses, in order:

1. .gitignore containing .env, .venv/, __pycache__/ — create it before the first commit.

2. Keep keys in .env, load with python-dotenv.

3. Rotate any key that ever touched a commit — assume it's compromised.

4. Run a secret scanner (e.g. gitleaks) before pushing; GitHub flags leaks automatically, but rotation is still your job.

This is a real interview filter question ('how do you handle secrets?') and a real production responsibility. Get it right from repo number one.

README: your code's storefront

A repo with no README is a locked shop. Every project repo you make in this course gets: a one-line description ('Support-ticket agent that classifies, retrieves, and answers — deployed'), a 30-second quickstart (pip install -r requirements.txt, cp .env.example .env, docker compose up), a screenshot or short demo GIF, an architecture note ('FastAPI → LangGraph agent → pgvector'), and a link to the live deployment. The README is what a recruiter sees in 15 seconds — the code is what an engineer sees at minute five. Both matter; Lesson 20 polishes this into a portfolio. Start the habit now.

Git for AI-specific work

AI repos have extra versioned artifacts: prompts, eval datasets, eval results, and deployment configs. Professionals commit prompt files as code (prompts/classify_v3.txt), version eval sets alongside the code that scores them, and record in the commit message which model and settings produced which score ('gpt-4o-mini, temp 0, 91% on eval v3 — up from 87%'). That traceability is what lets a team trust a prompt change. When your Lesson 12 evals run in CI on every push — yes, you'll do that — your repos become self-proving: code, prompts, and quality evidence in one public place.
