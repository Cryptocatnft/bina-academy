Structured Outputs and Schemas (JSON Mode, Pydantic)

🎯 What you'll be able to do: Make LLMs return reliable, validated JSON with schemas and Pydantic — the single technique that turns a chatbot into a component real software can trust.
Alex · Play the lecturer

Why free text breaks software

If a model answers 'Sure! The category is probably billing, I think 😊' — a human shrugs, a program crashes. Downstream code needs predictable structure: {"category": "billing", "confidence": 0.9}. Structured output means constraining the model to emit valid JSON matching a schema, every time. The provider-level tricks: JSON mode (forces syntactically valid JSON) and newer schema-constrained outputs, where you pass the exact shape and the API guarantees it. Combined with Pydantic on your side, you get a contract: if the model deviates, your code catches it — instead of your users catching it.

Pydantic: your schema is your validator

Pydantic lets you define the shape once and reuse it for prompting and validation:

`python

from pydantic import BaseModel, Field

class Ticket(BaseModel):

category: str = Field(..., description="one of: bug, billing, question")

urgency: int = Field(..., ge=1, le=5)

summary: str = Field(..., max_length=120)

resp = client.beta.chat.completions.parse(

model="gpt-4o-mini",

messages=[{"role": "user", "content": ticket_text}],

response_format=Ticket,

)

ticket = resp.choices[0].message.parsed # a real Ticket object

`

If the model returns garbage, Pydantic raises ValidationError — and you retry (Lesson 6). LangChain, FastAPI, and half the 2026 AI stack speak Pydantic natively. Learn it once, use it everywhere.

The full defensive loop

Production pattern, memorize it:

1. Define the schema (Pydantic).

2. Call the model with response_format=YourSchema.

3. Validate the parse; on failure, retry with the error message — models self-correct well: 'Your last output failed validation: urgency must be 1-5. Return corrected JSON only.'

4. Cap retries (2–3); then fall back (queue for human review, return None, or use a default).

This loop — schema, call, validate, retry-with-error — is the backbone of the agents you build in Lessons 11–16. It's also most of what 'LLM application engineering' means in job descriptions. Write it as a reusable function once; import it forever.

Enums, lists, and nested shapes

Scales of structure: an enum for classification ('bug'/'billing'/'question' — nothing else can come back), a list of nested objects for extraction (every invoice line with amount and date), and unions for routing (this request is a Refund or a Complaint). Practical rules that keep accuracy high: keep schemas flat and small — every field is another chance to err; give each field a clear description the model reads as instructions; and prefer many small structured calls over one mega-schema. You'll reuse exactly these schemas in RAG (Lesson 9) and the support agent (Lesson 13).
