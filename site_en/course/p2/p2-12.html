Evals and Observability: LLM-as-Judge Basics

🎯 What you'll be able to do: Prove your AI works — with test sets, LLM-as-judge evaluation, and tracing — the quality-control skill that turns 'it seems good' into 'it measurably improved, and here's the graph.'
Alex · Play the lecturer

Why 'it seems fine' isn't a quality bar

You change a prompt; three manual tests look okay; you ship; accuracy quietly drops 12%. Without evals, AI quality is invisible until users complain — or until your demo fails in front of a stakeholder. An eval suite is a fixed dataset plus automated scoring, run on every change. Three levels: unit checks (did it return valid JSON? did it cite sources?), golden-set scoring (accuracy on N known questions), and model-graded evals (an LLM judging open-ended output). The habit to build now: every project in Module 4 ships with its eval results in the README — a table of scores recruiters and interviewers can see.

Your first eval suite

Golden set: 20–50 real questions with known-good answers. Runner: same code path as production, offline scoring:

`python

def run_evals(cases, answer_fn, judge):

results = []

for c in cases:

out = answer_fn(c["question"])

score = judge(c["question"], out, c["expected"])

results.append({"id": c["id"], "score": score})

passed = sum(r["score"] >= 4 for r in results)

return {"pass_rate": passed / len(results), "results": results}

`

Store results as JSON per run, tagged with model + prompt version — this is your regression baseline. When you tune chunk size or prompts in the projects, you *re-run this* and show the delta. 'I improved RAG answer accuracy from 71% to 88% with these changes' is a resume bullet with receipts.

LLM-as-judge, done carefully

Open-ended output can't be string-matched, so a stronger model grades it against a rubric: 'Score 1–5: is the answer faithful to the sources? Penalize unsupported claims.' Rules that make judges reliable: a fixed rubric with explicit criteria; faithfulness first ('grounded in provided context, not general knowledge'); show the judge the sources; and calibrate on a human-labeled sample — run 10 cases graded by you and by the judge, compare, and adjust the rubric until they agree. Use a stronger model for judging than for generating. A good judge is itself a structured-output problem — Lesson 7 returns. Bias traps (verbosity, self-preference) exist; your calibration step is the defense.

Observability: traces, not vibes

Evals score the outcome; traces show the journey: every model call, tool invocation, latency, token count, and error, per request. Lightweight start — structured logging:

`python

import logging, time, json

log = logging.getLogger("agent")

t0 = time.time()

log.info("event=tool_call name=get_order id=%s", order_id)

# ... later ...

log.info("event=answer latency=%.2fs tokens=%d", time.time()-t0, n)

`

That's real observability in embryo — production teams graduate to platforms like LangSmith or OpenTelemetry, same concepts, nicer UIs. Wire your Lesson 11 agent's traces into an eval run and you can answer the interview classic: 'your agent's accuracy dropped this week — walk me through debugging it.' You'll have literally done it.

Copy-ready prompt

Design an eval suite for my [PROJECT: e.g. support agent with RAG]: golden-set categories, 15 example questions with expected behaviors, unit checks, and an LLM-as-judge rubric. Output as a table plus the rubric text.

Here are 5 real outputs from my agent with their sources: [PASTE]. As a strict judge, score each 1-5 for faithfulness and cite any unsupported claim. Then summarize the failure pattern.

My eval pass rate dropped from 88% to 74% after I changed [PROMPT/MODEL/CHUNKING]. Give me a systematic debugging procedure using traces and per-category eval breakdown to isolate the cause.
