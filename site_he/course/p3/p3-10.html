קודם מודדים: p50, p95 ועלות לבקשה

אופטימיזציה בלי מדידה זו אמונה, לא הנדסה. שלושה מספרים שכל מערכת חייבת לדווח: p50 ו-p95 של זמן עד טוקן ראשון (TTFT) ועד טוקן אחרון, עלות ממוצעת לבקשה, ופילוח לפי סוג בקשה.

`python

import time, statistics

lat = []

for req in sample:

t = time.time(); resp = call(req); lat.append(time.time() - t)

print(statistics.median(lat), sorted(lat)[int(len(lat)*0.95)])

`

p95 הוא המספר שהמשתמשים מרגישים — הם לא נמצאים בממוצע, הם בזנב. ועלות לפי סוג בקשה תגלה שעשרה אחוז מהמסלולים שורפים שישים אחוז מהתקציב. שם מתחילים.

שכבות cache

ארבע שכבות, מהזולה לחכמה: (1) prompt caching — קידומת קבועה בהתחלה (system + כלים), עד 90% הנחה על קלט; (2) cache של תוצאות מדויקות — פניות חוזרות זהות לפי hash של הודעות + גרסת פרומפט; (3) semantic cache — דומה מספיק (cosine מעל סף כמו 0.95) מחזיר תשובה שמורה — זהירות, מתאים לשאלות עובדתיות ולא לשיחות רגישות; (4) cache של תוצאות כלים — קריאת API יקרה שהסוכן עושה שוב ושוב, לפי TTL. לפני כל שכבה: מדידת hit rate. cache עם 5% פגיעות הוא סבל תחזוקה במקום חיסכון.

Batching: מה שלא צריך עכשיו זול יותר

רוב הספקים נותנים 50% הנחה על Batch API — הרצה אסינכרונית של אלפי בקשות בלי צורך בזמן אמת, תוצאות תוך שעות. מושלם ל: סיווג גושי מיילים, חילוץ נתונים מארכיון, יצירת אמבדינגים, בניית סטים. הכלל: כל מה שהמשתמש לא מחכה לו עכשיו — כמעט תמיד זול יותר ב-batch. מה שכן אינטראקטיבי — שם משחקים ב-latency: streaming (טוקן ראשון מהר מרגיש מהר פי שניים ממה שהוא), prefetch של כלים צפויים, ומקביליות של קריאות בלתי תלויות.

ראוטינג: המודל הזול קודם

לא כל בקשה צריכה את המודל הגדול. cascade: מנסים מודל זול, ומעלים רק אם יש סימן לחוסר ביטחון — פלט לא תקין, או classifier שמסמן מורכבות.

`python

def route(msg):

if simple_intent(msg):

return call('gpt-4o-mini', msg, fallback=True)

return call('gpt-4o', msg)

def call(model, msg, fallback=False):

out = run(model, msg)

if fallback and not valid(out):

return run('gpt-4o', msg)

return out

`

בפועל, 60–80% מהתעבורה נפתרת בזול. שמור מדידה: כמה בקשות הוסטו, ואיך הדיוק על סט הזהב — ראוטר שגוי ב-5% מהמקרים אוכל את החיסכון שלו בבאגים.
